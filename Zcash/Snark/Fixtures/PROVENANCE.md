# Verifier-fingerprint capture provenance

The four fixture families under this directory record concrete Rust verifier
executions and are consumed by Lean's `FixtureCheck` target. Their statement
of record is each family's `Boundary.lean` theorem
`nonInteractiveFingerprint_matches_derived`. The existing formats remain the
same: honest and random captures for one and two Actions, plus the random
families' `proof-bytes.hex` siblings.

These captures check the verifier model on the captured inputs. They do not
establish the Rust prover's masking distribution or universal Rust-to-Lean
correspondence. The zero-knowledge theorem concerns its Lean prover model;
its implementation assumption is described in
[the Zakura release provenance](../ZeroKnowledge/Zakura/PROVENANCE.md#lean-connection).

## Release target and recorded origin

The regeneration target is the post-NU6.3 prover/verifier in Zakura 1.4.0,
using Common `50f712ee22ca95e2dd5230c6f331ce2e433d70ee`. The
[release record](../ZeroKnowledge/Zakura/release.json) pins the source archives,
`zakura-orchard` and `zakura-halo2-proofs` 1.2.0, their published crate checksums,
and Common's toolchain and lockfile. The capture features and exporters already
ship in those packages; regeneration does not edit Rust sources.

[MANIFEST.tsv](MANIFEST.tsv) records the actual origin of each checked-in file:
path, SHA-256, generator, source revision, and invocation. All six artifacts were
regenerated by the four pinned Zakura capture tests. The capture tools carried
into the Zakura fork preserve the existing fixture formats.

The four random artifacts (both `Fixture.lean` files and their proof-byte siblings)
are byte-identical to the captures from Orchard 0.15.5 at
[`29d1d55db62153dcaeef8ef631c8991c53ed1248`](https://github.com/zcash/orchard/tree/29d1d55db62153dcaeef8ef631c8991c53ed1248).
Their SHA-256 values in the earlier Ironwood manifest match the regenerated files;
the current manifest records the Zakura reproduction of those same bytes. The
two honest captures changed when regenerated with the released prover.

## Rust capture paths

The [Orchard drivers](https://github.com/zakura-core/common/blob/50f712ee22ca95e2dd5230c6f331ce2e433d70ee/crates/orchard/src/circuit/fingerprint/mod.rs)
use `verifier-fingerprint`, forwarding to Halo2's `unstable-verifier-fingerprint`.
For honest captures, the driver builds a real bundle, creates and verifies its
proof, replays the bytes through `ChallengeRecorder`, and exports the verifier's
transcript and MSM with `dump_vesta_lean_fixture`. The captured MSM must evaluate
to the identity.

For random captures, the released fabricate-and-replay driver samples canonical
proof elements while following the verifier's read schedule, then replays the
bytes through the ordinary transcript recorder. Both runs must complete with
equal transcript events/challenges and a nonidentity MSM. The
[match-only exporter](https://github.com/zakura-core/common/blob/50f712ee22ca95e2dd5230c6f331ce2e433d70ee/crates/halo2_proofs/src/plonk/fingerprint/vesta_lean.rs)
checks coefficient agreement and emits a nonidentity certificate; it does not
claim that these are accepting proofs. The sampled points have known discrete
logs to the capture generator and are not an adversarial proof corpus.

The four drivers use `ChaCha20Rng::from_seed([seed; 32])`:

| Family | Seed |
| --- | --- |
| Honest one Action | `0x53` |
| Honest two Actions | `0x4d` |
| Random one Action | `0x52` |
| Random two Actions | `0x72` |

Fixed public seeds produce constants, not independent samples for a probability
theorem. Applying a sampling-based fingerprint bound to seeded captures needs its
stated generator/sampling assumption; these fixtures do not discharge it. The
released three-Action random driver is outside the four captured families used
here. A fixture match does not establish correspondence for every Action count.

## Regeneration and installation

Python 3.11 or later and the release's Rust toolchain are required for regeneration:

```sh
# Build the pinned Rust drivers and compare all six outputs with the repository.
scripts/regenerate-fingerprint-fixtures.sh

# Refresh the generated files and their provenance after the capture tests pass.
scripts/regenerate-fingerprint-fixtures.sh --update
```

The command authenticates sources/crates, uses Common's unmodified lockfile and
toolchain, and runs four exact capture tests with default release features and
one worker. It rejects zero-test runs and missing or changed outputs. It records
source hashes, command logs and output digests in a new directory under
`REGEN_WORK_DIR` (default `scripts/generated/zakura`, gitignored). Set
`ZAKURA_SOURCE_CACHE` or `--cache-dir` to reuse authenticated archives.

To reuse a completed capture run without running Rust again:

```sh
scripts/regenerate-fingerprint-fixtures.sh \
  --from-run /path/to/completed/fixtures --cache-dir /path/to/source-cache --update
```

`--update` writes whole generated artifacts and updates `MANIFEST.tsv` and the
single-Action capture pin in the release record together. It checks the captured
public generators/commitments against the release data before installation.
The existing Lean build and fixture checks must then pass; installation does not
claim those checks ran. CI omits `--update` and fails on any byte difference.

`--check-set` checks only the six-file inventory and exporter headers, without
Rust or network access. `scripts/check_fixture_manifest.sh` separately checks
all stored digests and provenance entries. CI runs these local guards on every
event and regenerates when capture inputs change or on its schedule/manual trigger.

## Separate circuit/layout dumps

The circuit-side artifacts in
[`Zcash/Circuits/Fixtures`](../../Circuits/Fixtures/PROVENANCE.md) come from a
separate dump pipeline with unpublished instrumentation. The verifier exporter
does not regenerate their JSON or selector maps. Because the circuit is unchanged,
those artifacts retain their original provenance and their existing Lean
reconstruction and content-pin checks.
